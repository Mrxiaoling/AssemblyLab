# 项目名称：Assembly Lab —— 汇编语言交互式学习与实验平台

## 一、项目目标

我希望开发一个完整的汇编语言学习实验室，帮助我从零开始理解汇编语言、CPU 执行机制、寄存器、内存、栈、函数调用、ABI、编译器生成的机器指令，以及汇编与高级语言之间的关系。

**不要把它开发成传统的汇编语言知识点教程。**

传统学习方式通常是：

- 学习寄存器有哪些。
- 学习 MOV、ADD、SUB 等指令。
- 学习寻址方式。
- 学习函数调用。
- 学习栈帧。
- 学习各种语法和规则。

这种方式非常枯燥，学完之后容易遗忘，也很难把不同知识点联系起来。

我希望采用另一种方式：

1. 从一个实际问题或者有趣的程序开始。
2. 运行程序，观察它的行为。
3. 查看编译器生成的汇编代码。
4. 进入逐指令执行模式。
5. 观察寄存器、内存、栈、标志寄存器的变化。
6. 通过可视化理解每条指令究竟做了什么。
7. 修改代码，预测运行结果，再执行验证。
8. 完成相关实验和课后习题。
9. 最后通过一个综合项目检验是否真正理解。

例如，学习函数调用时，不是直接讲 CALL 和 RET，而是提供一个 C++ 程序：

```
int add(int a, int b) {
    return a + b;
}

int main() {
    int result = add(10, 20);
    return result;
}
```

让用户亲自观察：

- C++ 代码如何变成汇编。
- 编译器如何传递参数。
- 参数存放在哪些寄存器中。
- CALL 指令做了什么。
- 返回地址存放在哪里。
- 函数如何建立栈帧。
- 返回值如何传递。
- RET 如何恢复执行位置。

最终让用户理解高级语言背后的底层机制。

## 二、目标用户和学习基础

目标用户具备一定的 C/C++ 编程经验，但汇编基础不系统。

学习过程中可以使用 C/C++ 作为对照语言。

希望重点建立以下能力：

1. 能够阅读 x86-64 汇编。
2. 能够阅读 ARM64/AArch64 汇编。
3. 能够理解常见 CPU 指令的执行效果。
4. 能够理解函数调用约定和 ABI。
5. 能够理解 C/C++ 编译后的代码结构。
6. 能够使用 GDB 等工具调试汇编程序。
7. 能够理解协程、上下文切换、异常处理等底层机制。
8. 能够结合嵌入式开发理解 ARM 汇编和处理器执行过程。
9. 能够阅读实际项目中的汇编代码，而不是只会写简单的汇编示例。

学习重点不是背诵指令，而是建立从高级语言到机器执行过程的完整认知。

## 三、总体产品设计

平台采用以下学习模式：

### 1. 场景驱动学习

每一节课都必须围绕一个实际问题、一个程序或者一个底层机制展开。

例如：

| 学习主题   | 实验场景                             |
| ---------- | ------------------------------------ |
| 寄存器     | 观察两个变量如何通过寄存器完成交换   |
| MOV 指令   | 观察数据如何在寄存器和内存之间移动   |
| 算术指令   | 实现一个简单计算器                   |
| 标志寄存器 | 观察有符号溢出和无符号进位           |
| 条件跳转   | 用汇编实现 if/else                   |
| 循环       | 用汇编实现数组遍历                   |
| 栈         | 观察局部变量和函数调用的内存布局     |
| CALL/RET   | 追踪一次完整函数调用                 |
| 函数参数   | 对比不同参数数量和类型的传递方式     |
| ABI        | 对比 Windows x64 和 System V AMD64   |
| 内存寻址   | 观察数组、结构体、指针的访问方式     |
| SIMD       | 使用 SSE/AVX 或 NEON 实现向量计算    |
| 原子指令   | 理解原子操作和锁的底层实现           |
| 协程       | 追踪 C++20 协程的挂起和恢复          |
| 上下文切换 | 理解寄存器、栈和执行上下文的保存恢复 |
| 异常处理   | 理解异常展开和相关运行时机制         |
| 中断       | 观察 ARM 异常向量表和中断入口        |
| 内存屏障   | 理解 CPU 内存顺序和屏障指令          |

每个实验必须有明确的学习目标和可观察的结果。

### 2. 交互式实验

这是整个项目最重要的功能。

用户不应该只看汇编代码，而应该能够操作代码并观察执行过程。

实验界面至少包括：

- 源代码编辑区。
- 汇编代码区。
- 反汇编区。
- 寄存器面板。
- 标志寄存器面板。
- 内存查看器。
- 栈内存查看器。
- 指令执行轨迹。
- 当前指令说明。
- 执行控制面板。

执行控制包括：

- 运行。
- 暂停。
- 单步执行。
- 单步进入函数。
- 单步跳出函数。
- 重置。
- 设置断点。
- 删除断点。
- 修改寄存器。
- 修改内存。
- 修改代码后重新编译。

每执行一条指令，界面都应该明确展示：

1. 当前执行的指令。
2. 指令执行前的寄存器状态。
3. 指令执行后的寄存器状态。
4. 哪些内存地址发生变化。
5. 哪些标志位发生变化。
6. 程序计数器如何变化。
7. 为什么发生这些变化。

例如：

```
mov rax, 10
mov rbx, 20
add rax, rbx
```

执行 ADD 后，界面应该展示：

```
执行前：

RAX = 10
RBX = 20

执行指令：

ADD RAX, RBX

执行后：

RAX = 30
RBX = 20
```

同时展示 RFLAGS 中相关标志位的变化。

注意：必须根据实际指令语义和模拟器执行结果生成状态变化，不能只通过字符串匹配指令来模拟。

## 四、体系结构支持

采用分阶段支持多种 CPU 架构。

### 第一阶段：x86-64

重点支持：

- Intel/AMD x86-64。
- NASM 语法。
- GNU AT&T 语法。
- Intel 汇编语法。
- System V AMD64 ABI。
- Windows x64 ABI。

主要寄存器：

- RAX、RBX、RCX、RDX。
- RSI、RDI、RBP、RSP。
- R8-R15。
- RIP。
- RFLAGS。
- XMM/YMM 基础寄存器。

### 第二阶段：ARM64/AArch64

重点支持：

- X0-X30。
- SP。
- PC。
- NZCV。
- W/X 寄存器关系。
- AAPCS64 调用约定。
- 函数调用和栈帧。
- LDR/STR。
- ADD/SUB。
- CMP/B。
- BL/RET。
- 条件执行和寻址模式。
- NEON 基础指令。

需要结合 ARM Linux 和嵌入式开发中的真实代码进行教学。

### 第三阶段：RISC-V

作为扩展架构：

- RV32I。
- RV64I。
- 基础整数指令。
- ABI。
- 函数调用。
- 栈帧。
- 中断和异常。

架构设计必须允许未来增加其他 ISA，不允许把 x86-64 的寄存器和指令逻辑写死在整个系统中。

### 第七阶段：C++20 协程底层原理

这是整个实验室的重点专题之一。

不能仅仅解释 co_await、co_yield、co_return 的语法。

必须通过实际 C++20 协程代码，分析编译器如何生成协程状态机，以及协程如何通过运行时机制挂起和恢复执行。

学习内容：

- 协程的基本概念。
- 协程状态机。
- Coroutine Frame。
- Promise Type。
- Coroutine Handle。
- Initial Suspend。
- Final Suspend。
- Awaitable。
- Awaiter。
- await_ready。
- await_suspend。
- await_resume。
- co_await。
- co_yield。
- co_return。
- 协程帧的分配和释放。
- 挂起点和恢复点。
- 局部变量生命周期。
- 保存和恢复执行上下文。

实验代码：

```
#include <coroutine>
#include <iostream>

struct Task {
    struct promise_type {
        Task get_return_object() {
            return {};
        }

        std::suspend_always initial_suspend() noexcept {
            return {};
        }

        std::suspend_always final_suspend() noexcept {
            return {};
        }

        void return_void() {}

        void unhandled_exception() {
            std::terminate();
        }
    };
};

Task foo() {
    std::cout << "A\n";
    co_await std::suspend_always{};
    std::cout << "B\n";
}
```

需要通过实验观察：

1. 协程调用时发生了什么。
2. 协程帧在哪里分配。
3. 协程帧中保存了哪些数据。
4. promise_type 如何参与协程生命周期。
5. co_await 如何转化为底层调用。
6. 协程挂起时保存了哪些状态。
7. 恢复时如何找到下一条需要执行的逻辑。
8. 局部变量为什么可以跨越挂起点继续存在。
9. 协程句柄 resume() 最终做了什么。
10. 协程结束后如何释放资源。

特别要求：

**提供协程执行可视化。**

界面同时展示：

- 原始 C++ 协程代码。
- 编译器生成的等价状态机示意。
- 反汇编代码。
- 当前执行位置。
- Coroutine Frame 内存布局。
- Promise 对象状态。
- 协程状态。
- 栈和寄存器变化。
- 挂起和恢复的时间线。

对于使用特定编译器生成的汇编，必须明确标注编译器版本、目标架构和编译参数。

不要把某个编译器的实现细节说成 C++ 标准的强制要求。

- 执行轨迹。
- 指令前后状态对比。
- 错误指令提示。

优先考虑复用成熟的模拟器或指令执行引擎，例如 Unicorn Engine、QEMU 等。

必须调研不同方案的功能、授权、集成难度和跨平台能力，再决定是否自研。

如果使用模拟器，必须明确它模拟的是指令语义，不等于真实 CPU 的微架构执行过程。

### 模式 B：真实程序调试

用于 C/C++ 和真实汇编代码。

建议使用：

- GCC。
- Clang。
- NASM。
- GNU Assembler。
- GDB。
- LLVM 工具链。
- objdump。
- readelf。
- QEMU（必要时）。

支持：

- 编译 C/C++。
- 生成汇编。
- 反汇编。
- 查看 ELF 信息。
- 查看符号表。
- 设置断点。
- 单步执行。
- 查看寄存器。
- 查看内存。
- 查看调用栈。

真实程序调试应优先复用 GDB/MI 或其他成熟调试接口，不要自行重新实现完整调试器。

### 执行安全

用户代码属于不可信输入。

必须考虑：

- 运行隔离。
- 超时限制。
- 内存限制。
- CPU 资源限制。
- 禁止任意访问宿主机文件。
- 禁止任意网络访问。
- 禁止危险系统调用。
- 编译和运行任务独立管理。
- 清理临时文件。
- 资源泄漏防护。

不能把仅仅设置程序超时当成完整的沙箱。

如果某种执行模式暂时无法做到安全隔离，必须明确标记，并默认不允许执行不可信代码。

## 八、课后习题系统

课后习题不能只是选择题。

必须提供多种题型。

### 1. 预测执行结果

给出一段汇编：

```
mov rax, 5
mov rbx, 3
sub rax, rbx
```

要求用户预测：

- RAX 最终值。
- RBX 最终值。
- 相关标志位。
- RIP 的变化。

### 2. 补全汇编

给出不完整代码，要求用户补全指令。

### 3. 汇编转 C++

给出汇编代码，要求用户写出等价的 C++ 代码。

### 4. C++ 转汇编分析

给出 C++ 代码，要求用户解释对应的汇编逻辑。

### 5. Bug 修复

提供一段存在错误的汇编代码，要求用户找出问题。

### 6. 调试挑战

提供一个可以运行的程序，但隐藏关键问题。

要求用户通过寄存器、内存和执行轨迹找到问题。

### 7. 综合编程

例如：

- 实现数组求和。
- 实现字符串长度计算。
- 实现简单排序。
- 实现函数调用。
- 实现一个简化版协程调度器。
- 使用原子指令实现自旋锁。

### 8. 原理解释

要求用户用自己的语言解释某个机制。

例如：

- 为什么 CALL 会影响栈？
- 为什么局部变量可以跨越协程挂起点存在？
- 为什么不同 ABI 的参数传递方式不同？
- 为什么优化后的代码可能没有对应的源代码结构？

### 习题反馈机制

每道题必须提供：

- 题目目标。
- 难度。
- 涉及知识点。
- 输入条件。
- 预期结果。
- 自动判题条件。
- 参考答案。
- 详细解析。
- 常见错误。
- 关联实验。

不要在用户第一次提交错误答案时直接显示完整答案。

建议：

第一次错误：给出方向性提示。

第二次错误：给出更具体的提示。

用户主动查看答案：展示完整解析。

对于需要解释原理的题目，可以支持 AI 辅助评价，但不能把没有可靠依据的自动评价当作标准答案。
